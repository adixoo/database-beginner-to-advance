Rows sit in pages ([How rows are stored](/advanced/how-rows-are-stored)), and the column names and types sit in the catalog ([How the schema is stored](/advanced/how-the-schema-is-stored)). Now the trip back: how a `SELECT` finds a row. There are two ways, depending on whether the column in your `WHERE` has an index. These examples use the `notes` table.

## With an index

```sql
SELECT * FROM notes WHERE id = 3;
```

`id` is the primary key, so it already has an index. The database answers in three steps:

### Find the row's page and slot

<RecordIdLookup />

1. The [index](/beginner/indexes) on `id` is a sorted list of every `id` with its row's **address**.
2. The database looks up `3` in the index. Its address is page 0, slot 3.
3. It jumps to page 0 in the file, then to slot 3 inside it. That is row 3.

The address has a different name in each engine:

| Engine         | A row's address is…                                                                  |
| -------------- | ------------------------------------------------------------------------------------ |
| PostgreSQL     | Called `ctid`: the page and slot, as above. See it with `SELECT ctid, * FROM notes;` |
| MySQL (InnoDB) | The primary key itself, which leads to the right page                                |
| SQLite         | The `rowid`, which is also the primary key                                           |

## Without an index

```sql
SELECT * FROM notes WHERE body = 'Book the trek';
```

`body` has no index, so there is no list of addresses to look in. The database has to read the whole table. This is a **full table scan**:

The database cannot stop at the first match: a row on a later page might match too. With 3 rows this is instant. With a million rows over thousands of pages, every one of those pages is read.

## Which way did the database go?

Ask the database for its plan. Each engine names the two ways differently:

| Engine         | Ask with                      | With an index | Without an index |
| -------------- | ----------------------------- | ------------- | ---------------- |
| PostgreSQL     | `EXPLAIN SELECT …`            | `Index Scan`  | `Seq Scan`       |
| MySQL (InnoDB) | `EXPLAIN SELECT …`            | type `const`  | type `ALL`       |
| SQLite         | `EXPLAIN QUERY PLAN SELECT …` | `SEARCH`      | `SCAN`           |

Try both queries in SQLite:

```sql
EXPLAIN QUERY PLAN SELECT * FROM notes WHERE id = 3;

EXPLAIN QUERY PLAN SELECT * FROM notes WHERE body = 'Book the trek';
```

```text
SEARCH notes USING INTEGER PRIMARY KEY (rowid=?)
SCAN notes
```

Add an index on `body`, and the scan becomes a search:

```sql
CREATE INDEX idx_notes_body ON notes (body);

EXPLAIN QUERY PLAN SELECT * FROM notes WHERE body = 'Book the trek';
```

```text
SEARCH notes USING INDEX idx_notes_body (body=?)
```

[Choosing indexes well](/advanced/choosing-indexes) covers which columns deserve one.

## Words to know

<WordsToKnow>

- **Buffer pool**
  The part of memory where a database keeps copies of pages it has read.
- **Full table scan**
  Reading every page of a table and checking every row, because no index can help.
- **Index**
  A sorted list of a column's values, each with the address of its row.
- **Row address**
  What leads the database to one row: a page and slot, or a key.

</WordsToKnow>
