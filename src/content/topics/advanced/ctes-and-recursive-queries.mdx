A **common table expression (CTE)** is a named query that lives for one statement. You write it with `WITH`, then use its name like a table.

Here is a small company, where each employee points to their manager:

```sql
CREATE TABLE employees (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  title TEXT NOT NULL,
  manager_id INTEGER REFERENCES employees (id),
  salary INTEGER NOT NULL
);

INSERT INTO employees (id, name, title, manager_id, salary) VALUES
  (1, 'Asha', 'CEO', NULL, 300),
  (2, 'Ravi', 'CTO', 1, 200),
  (3, 'Meera', 'CFO', 1, 190),
  (4, 'Kabir', 'Engineer', 2, 120),
  (5, 'Zoya', 'Engineer', 2, 115),
  (6, 'Dev', 'Intern', 4, 40),
  (7, 'Isha', 'Accountant', 3, 90);
```

Salaries are in thousands. Asha has no manager, so her `manager_id` is `NULL`.

## WITH: name a step

Without a CTE, a query with a grouped [subquery](/beginner/subqueries) reads inside out. With one, it reads top to bottom:

```sql
WITH teams AS (
  SELECT manager_id, COUNT(*) AS reports, AVG(salary) AS avg_salary
  FROM employees
  WHERE manager_id IS NOT NULL
  GROUP BY manager_id
)
SELECT e.name, t.reports, t.avg_salary
FROM teams AS t
JOIN employees AS e ON e.id = t.manager_id
ORDER BY t.reports DESC, e.name;
```

| name  | reports | avg_salary |
| ----- | ------: | ---------: |
| Asha  |       2 |      195.0 |
| Ravi  |       2 |      117.5 |
| Kabir |       1 |       40.0 |
| Meera |       1 |       90.0 |

## Several CTEs in a row

Separate CTEs with commas. Each one can use the ones before it:

```sql
WITH company AS (
  SELECT AVG(salary) AS avg_pay FROM employees
),
above_average AS (
  SELECT name, salary FROM employees, company WHERE salary > company.avg_pay
)
SELECT * FROM above_average ORDER BY salary DESC;
```

| name  | salary |
| ----- | -----: |
| Asha  |    300 |
| Ravi  |    200 |
| Meera |    190 |

The company average is 1055 / 7 ≈ 150.7, so three people are above it.

## CTE, subquery or view?

|                     | CTE                   | Subquery            | [View](/beginner/views) |
| ------------------- | --------------------- | ------------------- | ----------------------- |
| Lives for           | One statement         | One spot in a query | Until you drop it       |
| Use it twice        | Yes, by name          | No, copy it         | Yes, from any query     |
| Can call itself     | Yes, with `RECURSIVE` | No                  | No                      |
| Saved in the schema | No                    | No                  | Yes                     |

Pick a CTE to make one long query readable, and a view when many queries need the same logic.

<Callout type="info">

Is a CTE slower? Usually not. PostgreSQL 12+ and SQLite fold a simple CTE into the main query, just like a subquery. Before version 12, PostgreSQL always ran each CTE on its own first, which sometimes blocked the optimizer. You can still choose with `WITH x AS MATERIALIZED (...)` or `AS NOT MATERIALIZED (...)`.

</Callout>

## WITH RECURSIVE: walk a tree

"Everyone under Asha, with their level" is impossible with a fixed number of joins, because you don't know how deep the tree goes. A **recursive CTE** has two parts joined by `UNION ALL`:

1. The **anchor**: the starting rows.
2. The **recursive part**: joins the CTE to the table to find the next level.

```sql
WITH RECURSIVE org (id, name, depth, path) AS (
  SELECT id, name, 0, name
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  SELECT e.id, e.name, org.depth + 1, org.path || ' > ' || e.name
  FROM employees AS e
  JOIN org ON e.manager_id = org.id
)
SELECT depth, path FROM org ORDER BY path;
```

| depth | path                      |
| ----: | ------------------------- |
|     0 | Asha                      |
|     1 | Asha > Meera              |
|     2 | Asha > Meera > Isha       |
|     1 | Asha > Ravi               |
|     2 | Asha > Ravi > Kabir       |
|     3 | Asha > Ravi > Kabir > Dev |
|     2 | Asha > Ravi > Zoya        |

The database runs it in rounds. Each round only sees the rows the round before found:

```text
round 0 (anchor)    Asha
round 1             Ravi, Meera          ← managed by Asha
round 2             Kabir, Zoya, Isha    ← managed by Ravi or Meera
round 3             Dev                  ← managed by Kabir
round 4             (nothing)            → stop
```

The same shape works for comment threads, folders, categories and bill-of-materials parts.

## Walking up instead of down

Swap the join to go from a person up to the top:

```sql
WITH RECURSIVE chain (id, name, manager_id, steps_up) AS (
  SELECT id, name, manager_id, 0 FROM employees WHERE name = 'Dev'
  UNION ALL
  SELECT e.id, e.name, e.manager_id, chain.steps_up + 1
  FROM employees AS e
  JOIN chain ON e.id = chain.manager_id
)
SELECT steps_up, name FROM chain ORDER BY steps_up;
```

| steps_up | name  |
| -------: | ----- |
|        0 | Dev   |
|        1 | Kabir |
|        2 | Ravi  |
|        3 | Asha  |

## Guard against loops

If bad data makes a loop (Asha's manager is Dev, Dev's is Kabir, … back to Asha), the recursion never ends. Add a guard:

```sql illustration
-- Stop at a sane depth
SELECT e.id, e.name, org.depth + 1, org.path || ' > ' || e.name
FROM employees AS e
JOIN org ON e.manager_id = org.id
WHERE org.depth < 50
```

- A **depth limit**, as above, always stops.
- `UNION` instead of `UNION ALL` drops rows already seen, but only exact duplicates: with a `depth` column every row is new, so it won't help here.
- PostgreSQL 14+ has a built-in `CYCLE id SET is_cycle USING path` clause that marks and stops loops.

## Generate rows from nothing

A recursive CTE can make rows, such as every day in a range. Reports use this to show days with no sales as zero, by `LEFT JOIN`-ing the real data onto it:

```sql
WITH RECURSIVE days (day) AS (
  SELECT '2026-11-01'
  UNION ALL
  SELECT date(day, '+1 day') FROM days WHERE day < '2026-11-07'
)
SELECT day FROM days;
```

```text
2026-11-01
2026-11-02
…
2026-11-07
```

The `WHERE` in the recursive part is the stop condition. PostgreSQL has a shortcut for this: `generate_series('2026-11-01'::date, '2026-11-07', '1 day')`.

## Words to know

<WordsToKnow>

- **Anchor**
  The first part of a recursive CTE, which gives the starting rows.
- **CTE (common table expression)**
  A named query, written with WITH, that lives for one statement.
- **Cycle**
  A loop in the data, such as two rows that are each other's parent.
- **Recursive CTE**
  A CTE that refers to itself, adding rows round by round until a round finds none.

</WordsToKnow>
